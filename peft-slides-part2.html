What is quantization?

Quantization maps a continuous, high-precision number to one of a small, fixed set of representable values, storable in far fewer bits. With $b$ bits you get exactly $2^b$ representable levels — 4 bits means 16 possible values for every weight.

$$x_{int} = \operatorname{clamp}\!\big(\lfloor x/s\rceil + z,\ 0,\ 2^b-1\big), \qquad \hat x = s\,(x_{int}-z)$$

$x$ — the original value; $s$ — the scale; $z$ — the integer zero-point; $b$ — the bit-width; $x_{int}$ — the stored integer; $\hat x$ — the dequantized approximation, used whenever the weight is actually multiplied.

Calibrate once per tensor from its observed range $[x_{min},x_{max}]$: $s=\dfrac{x_{max}-x_{min}}{2^b-1}$, $z=\operatorname{round}(-x_{min}/s)$ — so $z$ is just the integer code that $x=0$ maps to. With $b=4$ and range $[-2,6]$: $s=\frac{6-(-2)}{15}=0.533$, $z=\operatorname{round}(2/0.533)=4$:

Why bother, and why clamp?

Bit-width sets memory directly: fp32 → 32 bits/weight, bf16 → 16, int8 → 8, int4 (like NF4) → 4 — a 4× reduction going 16-bit to 4-bit. Clamping matters for the last row: $9.0$ is outside the calibrated range, so $x/s+z=21$ would need a 5th bit; clamp forces it to the nearest valid code ($15$) instead of overflowing — at the cost of a much larger error ($3.13$ vs. $\le 0.13$ for in-range values).

QLoRA

QLoRA backpropagates LoRA's $B,A$ gradients through a frozen base model held in 4-bit precision — this is what "quantization-aware LoRA" means in practice.

4-bit NormalFloat

A data type tuned to how pretrained weights are actually distributed (roughly normal), so 4 bits capture more information than a generic 4-bit float.

Double quantization

The quantization constants themselves are quantized again, shrinking memory further.

Paged optimizers

Optimizer states spill to CPU memory on demand, avoiding out-of-memory spikes.

Headline result

Fine-tunes a 65B-parameter model on a single 48GB GPU, matching full 16-bit fine-tuning quality.

NF4: where the 16 levels come from

Pretrained weights are roughly normally distributed, so NF4 places its 16 levels at the quantiles of a standard normal $N(0,1)$ — each level covers an equal slice of probability, not an equal slice of the number line:

$$q_i=\tfrac12\Big(Q_X\big(\tfrac{i}{2^k+1}\big)+Q_X\big(\tfrac{i+1}{2^k+1}\big)\Big)$$

$Q_X$ — the quantile function (inverse CDF) of $N(0,1)$; $k=4$ is the bit-width; $q_i$ is the midpoint of two adjacent quantiles out of $2^k+1=17$. Since $N(0,1)$ has mean $0$, $Q_X$ is antisymmetric about $p=0.5$, so this grid's exact-zero index $q_{2^{k-1}}$ only cancels to $0$ if the two quantile evaluations round identically — fragile in floating point. NF4 sidesteps relying on that cancellation: build two half-tables at reduced resolution — 8 quantiles for the negative side, 9 for the positive side, each via the same formula — then merge them, sharing one endpoint fixed at exactly $0$. Rescale by the largest $|q_i|$ so everything fits in $[-1,1]$, giving the fixed, precomputed table every weight gets snapped to, next slide onward:

QLoRA: from weights to 4-bit codes

Real weights aren't already sitting in $[-1,1]$ — NF4 has to get them there first. Weights are grouped into small blocks (64 weights per block in practice), and every block goes through the same four steps:

  1. Find the scale. $s=\max_i|w_i|$ — the largest magnitude in the block.
  2. Normalize. Divide every weight by $s$, so the whole block now lies in $[-1,1]$: $\tilde w_i = w_i/s$.
  3. Snap to the nearest level. Compare $\tilde w_i$ to the 16 NF4 quantile levels and keep only the 4-bit index of the closest one.
  4. Store. One 4-bit index per weight, plus a single shared scale $s$ for the whole block.
Getting a weight back — concretely

Say a weight's stored 4-bit index is 1000 (decimal 8). Look up index 8 in the fixed 16-value table $\to 0.080$. Multiply by the block's scale, say $s=0.88$: $\hat w = 0.080\times0.88=0.070$. That's the number actually used in the matrix multiply — the original weight might have been $0.05$; the small gap is quantization error. This lookup-then-scale happens on the fly, right before each matrix multiply, never stored.

What actually gets stored

8 weights × 4 bits + one 32-bit scale = 64 bits for this block — vs. $8\times16=128$ bits at fp16, already a 2× saving here, and real 64-weight blocks push this much further since one scale is shared over far more weights. QLoRA: what's used where

Two different objects flow through QLoRA, stored and used differently:

Base weight $W_0$

Stored in 4-bit, always — during fine-tuning and at inference alike. Every forward pass, each block is dequantized on the fly to bf16 right before its matmul, then discarded. $W_0$ never receives a gradient and is never updated.

LoRA's $B,A$

Kept in bf16 throughout — small enough that quantizing them wouldn't save much, and they need to accumulate gradients precisely. Trained during fine-tuning; frozen (but still applied) at inference.

Both stages run the same computation, $h=\operatorname{dequant}(W_0)x+\tfrac{\alpha}{r}(xB)A$ — training additionally tracks gradients through it, into $B,A$ only; inference just evaluates it.

Merging is possible — it just undoes the point

Plain LoRA merges $B,A$ into $W_0$ once, offline, before deployment — inference then runs a single matmul at zero added cost (an earlier slide). QLoRA could do the same: dequantize $W_0$ to bf16, add $\tfrac{\alpha}{r}BA$, store the result. But that merged model is bf16-sized again — it throws away the 4-bit memory saving that was the whole reason to quantize $W_0$. So QLoRA keeps $W_0$ and $B,A$ unmerged and pays for it on every forward pass: dequantizing each block on the fly, plus a separate small matmul, both of which a merged model would skip. This is genuinely extra latency versus plain LoRA — the trade for a much smaller resident model.

This is what "NF4 is information-theoretically optimal for normal data" actually means — a population-level guarantee, not a promise for any single block.

QLoRA: double quantization in numbers

Every block of $64$ weights shares one scale constant $s$, normally stored in 32-bit float — that's a real, per-parameter memory cost on top of the 4-bit weights themselves:

$$\text{overhead} = \frac{32\text{ bits}}{64\text{ weights}} = 0.5\text{ bits/weight}$$

Double quantization quantizes those scale constants too: every 256 of them (themselves covering $256\times64=16{,}384$ weights) share one 32-bit meta-constant, and each individual scale is stored in only 8 bits:

$$\text{overhead} = \frac{256\times8\text{ bits} + 32\text{ bits}}{16{,}384\text{ weights}} = \frac{2080}{16{,}384} \approx 0.127\text{ bits/weight}$$
At model scale

$0.5-0.127=0.373$ bits saved per weight. Across a 65-billion-parameter model, that's $0.373\times65\text{B}$ bits $\approx$ 3.0 GB of GPU memory recovered — from compressing numbers that were only ever there to describe other numbers.

QLoRA: paged optimizers

Adam's optimizer state ($m$, $v$ per trainable parameter) is small for LoRA's $B,A$ — but GPU memory use isn't perfectly flat during training. Operations like gradient-checkpoint recomputation cause short-lived spikes above the steady-state usage.

Without paging

The GPU must be provisioned for the peak, not the average. Suppose steady-state training fits in 20GB but one recomputation step briefly needs 24GB — on a 22GB GPU, that spike alone crashes the run, even though it happens for a fraction of a second.

With paging

Paged optimizers use NVIDIA unified memory: pages of optimizer state not needed right now are automatically migrated to CPU RAM when the GPU is under pressure, and paged back in when needed — the same idea an operating system uses to page virtual memory to disk. The 22GB GPU survives the 24GB spike by briefly borrowing 2GB of CPU RAM, then returns to normal.

DoRA: weight-decomposed LoRA

DoRA splits a weight matrix into two independent pieces — a magnitude and a direction — and applies LoRA only to the direction.

$$W = m\cdot\frac{V}{\lVert V\rVert_c}$$

$V$ — the direction matrix, initialized to $W_0$; $\lVert V\rVert_c$ — its column-wise norm, so $V/\lVert V\rVert_c$ has unit-norm columns; $m$ — a separately trained magnitude vector, one scalar per column, initialized to $\lVert W_0\rVert_c$.

LoRA's update is applied only inside the direction term: $V = W_0 + BA$. Training $m$ and $B,A$ separately lets the model adjust a column's length and its orientation independently — closing more of the gap to full fine-tuning than plain LoRA, at no extra inference cost.

DoRA: a numeric example

Reuse LoRA's $W_0$ and update: $V'=W_0+\tfrac{\alpha}{r}BA=\begin{bmatrix}4&5\\2&5\\1&2\end{bmatrix}$, column norms $\lVert V'\rVert_c\approx[4.58,\,7.35]$.

If $m$ were left passive at $\lVert V'\rVert_c$, DoRA would just reproduce plain LoRA's $W'$. Suppose training instead finds an independent $m_{\text{learned}}=[5.0,\,6.5]$:

$$W_{\text{DoRA}}=m_{\text{learned}}\cdot\frac{V'}{\lVert V'\rVert_c} =\begin{bmatrix}4.36&4.42\\2.18&4.42\\1.09&1.77\end{bmatrix} \qquad\text{vs. plain LoRA's}\qquad W'=\begin{bmatrix}4&5\\2&5\\1&2\end{bmatrix}$$
Same B, A — different weight

The direction update is identical to plain LoRA's, but the final weight matrix visibly differs, because $m$ was free to land somewhere other than the column norm $BA$ would have produced on its own. That extra degree of freedom is what closes more of the gap to full fine-tuning.

AdaLoRA: adaptive rank allocation

Plain LoRA gives every weight matrix the same fixed rank $r$. AdaLoRA instead parameterizes each update in SVD form and lets the rank vary by importance.

$$\Delta W \approx P\Lambda Q$$

$P\in\mathbb{R}^{d\times r}$, $Q\in\mathbb{R}^{r\times d_{out}}$ — like LoRA's $B,A$, but regularized to stay near-orthonormal; $\Lambda=\operatorname{diag}(\sigma_1,\dots,\sigma_r)$ — singular-value-like weights, one per rank triplet.

During training, each triplet $(p_i,\sigma_i,q_i)$ gets an importance score; low-importance triplets are pruned ($\sigma_i\to0$) and the freed rank budget is reallocated to more important matrices — so more useful layers end up with higher effective rank than less useful ones, for the same total parameter budget.

AdaLoRA: why SVD

Take $M=\begin{bmatrix}3&1&2\\2&4&1\\1&1&5\end{bmatrix}$, singular values $\sigma=[6.78,\,3.56,\,1.82]$. Keeping only the largest, $r=1$:

$$M_1=\sigma_1u_1v_1^\top,\qquad \lVert M-M_1\rVert_F = 4.00$$

Compare against a different, non-SVD rank-1 guess — keep only the top-left entry, zero everything else:

$$M_{\text{arb}}=\begin{bmatrix}3&0&0\\0&0&0\\0&0&0\end{bmatrix}, \qquad \lVert M-M_{\text{arb}}\rVert_F = 7.28$$
Eckart–Young, confirmed

$4.00 < 7.28$ — truncated SVD's error is smaller, and it's provably the smallest possible among every rank-1 matrix, not just this one alternative. That's why AdaLoRA parameterizes its update in SVD form: the singular values say exactly which rank-1 pieces are safest to drop.
